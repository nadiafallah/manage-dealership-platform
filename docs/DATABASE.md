## 0017: parts workbench

`0017_parts_workbench.sql` adds nullable sale price, handover actor, confirmed consumption and return details to `part_requests`. It creates tenant-scoped `external_contractors`, `external_work` (one per existing planned task) and immutable application snapshots in `parts_statements` (unique case/version per tenant). Existing deliveries remain intact and consumption is confirmed explicitly. The shared official Emdad import and existing exact-stock reservation tables keep their history. All new writes record audit/change-log entries in the same transaction.

The matching `0017_parts_workbench.down.sql` is for disposable rehearsal data. Retain additive schema when rolling back application images. See [staff instructions](PHASE2_PARTS_FA.md).

## 0014: repair workflow, station codes and market-price approvals

`0014_parallel_mattie_franklin.sql` adds tenant-scoped `work_calendars` (append-only effective revisions), `workshop_stations` (mutable/versioned), and `part_quotes` (versioned proposal and external-decision history). Task rows gain station/assignee references, a station snapshot, a frozen calendar snapshot and immutable original planned start/end timestamps. Existing tasks retain null snapshots/baselines; no historical durations, assignments or customer data are invented. Every mutation writes audit and change-log snapshots in the same transaction. Cross-tenant station, staff, quote and case references are validated by services. Code uniqueness is scoped to the tenant.

Matching rollback: `apps/api/src/db/down/0014_parallel_mattie_franklin.sql`. It drops the new history and task columns; it is destructive and requires preservation/review before any real execution. The SQL migration does not modify real accounts, role assignments, permission templates, passwords or MFA. New default role permissions still require an effective-access review before rollout, because pre-existing templates/overrides take precedence. See [workflow guide](ACCIDENT_WORKFLOW_FA.md).

Migration `0013_stock_code_aliases` adds tenant-scoped, versioned human-approved family aliases for nonstandard stock codes. A nullable base detaches an alias without losing its audited history. Snapshot quantities, source codes and existing reservations are unchanged. Migrations 0012 and 0013 were restored/rehearsed and installed in production on 2026-11-03 with release 40b389f; sample daily reports were applied only to the isolated copy, never production.

## Conventions

- Primary keys: UUIDv7 generated by the application (time-ordered, unique across nodes).
- `tenant_id` on every tenant-owned table. Every service query filters by the actor's tenant.
- `version integer` on mutable rows; updates use `WHERE version = :expected` and bump it (optimistic locking, sync conflict detection).
- `timestamptz` everywhere, stored in UTC.
- `is_test boolean` marks synthetic rows; `pnpm db:reset-demo` deletes only tenants with `is_test = true` and their rows.
- Unknown values are stored as `NULL` and listed in `cases.missing_fields` — never placeholders.

## Status values

- Case stage: `reception → assessment → awaiting_approval → awaiting_parts → in_repair → quality_control → ready_for_delivery → delivered`. Status: `open | closed | cancelled`.
- Task status: `pending → in_progress → done → approved`, with `blocked` (via blockers) and reopen (`done|approved → in_progress`, reason required).
- Blocker reasons: see `BLOCKER_REASONS` in `packages/shared/src/enums.ts`.
- Part status: `needed → reserved | ordered → received | rejected → handed_over`, or `cancelled`. Finance approval: `proposed → approved | rejected`, advance `approved → paid`.
- Assessment status: `draft → final → superseded`. Authorization: `pending | not_required | approved | partially_approved | rejected`. Item approval: `pending | approved | rejected`.

## 0008_vehicle_import

Existing-vehicle Excel import. On `cases`: `admission_no` (workshop admission card number, original text) and `admission_no_key` (matching key; null for non-unique values such as «بدون پذیرش»), `admitted_at_precision` ('minute' default, 'date' when only the day is known), `origin` ('manual' | 'excel_import') and `import_key` (identity used by the import: vin:, adm: or chs:; unique per tenant when set, so an interrupted or repeated import cannot create a second case). `vehicles.chassis_ref`: chassis number as recorded on the sheet, never treated as a VIN. `tasks.import_ref` (unique per case when set): a sheet row's next action is created once. Rows are the provenance of imported cases. Additive; existing cases default to manual/minute. Down script `down/0008_vehicle_import.down.sql` (disposable databases only).

## 0006_staff_invitation_email

Additive columns on auth_challenges: invitation_delivery (manual/sending/sent/failed; default manual for existing data) and invitation_sent_at (nullable UTC timestamp). ## 0009_part_discrepancies

## 0011_staff_access

Additive `tenants.permission_templates` (role presets) and `permission_version`, plus `users.permission_overrides` (allow/deny) and `is_owner` (default false). Partial unique tenant owner index prevents multiple owner designations. No ownership is guessed by migration. Effective permissions: union of tenant role presets (fallback to code defaults), add personal allow, remove personal deny; designated owner has the complete catalog. Auth resolves these for every request. Owner-only mutations lock the tenant, use expected user/template versions and write audit/change-log transactionally. Invitation delegation cannot exceed the non-owner caller’s effective permissions after an owner exists. Current credentials, TOTP, sessions, case data and reference data are preserved. Application rollback retains columns; `down/0011_staff_access.down.sql` is for disposable databases only. See [staff workspaces and access](WORKSPACES_ACCESS_FA.md).

## 0018 — reminders, technician wages, responsibility periods

Phase 3, additive only: four new tables; no existing column is changed, renamed or dropped and no existing row is touched (no backfill).

- `reminders` (sender, optional case and plate, text of at most 300 characters checked by the API, urgency `normal`/`urgent`, source `manual`/`manager_report`/`technician_problem`, optional `target_role`) and `reminder_recipients` (one row per recipient: `sent` → `seen` → `done`, `seen_at`, `done_at`, one-line `reply`, `remind_at` = two working hours after sending by the dealership calendar at that moment, `reminded_at`, `version`). Unique on reminder + user. The unseen nudge is a row in the existing `notifications` table (dedupe key `reminder:<recipient>`), written once by the server loop that already sends the daily-report reminders. Sending, seen, done and reply are audited (`reminder.*`).
- `technician_wages`: one row per job (`task_id` primary key) with `amount_rial`, the reason of the last change, who set it and when, `seen_amount_rial`/`seen_at` (what the technician last saw, for the «تغییر کرد» label) and `version`. Independent from assessment labour. Every amount is audited as `task_wage` (`wage.set`, `wage.changed` with the required reason, `wage.seen`); the history is read from the audit, not duplicated. A wage counts in the monthly work only while its job is `approved` (approval time decides the Jalali month).
- `case_responsibility_periods`: who was responsible from `started_at` to `ended_at` (null = current), reason and origin (`created`, `initial`, `transfer`, `update`). A partial unique index allows at most one open period per case. Cases recorded before 0018 have no rows; their single computed period is admission → now with the current responsible. The first change writes that computed period (`initial`) and opens the next one, so earlier data is never rewritten. Report events filtered by responsible use the period in force at the event time.
- Demo reset (`purgeTestTenants`) deletes these rows, plus `notifications` and `case_alert_responses`, before cases, tasks and users of synthetic tenants.

Verified locally on PostgreSQL 16: all migrations `0000`→`0018` on an empty database, the down script and a re-apply, and the one-open-period index. Rollback: the previous application ignores the new tables; `down/0018_people_reminders_wages.down.sql` is for disposable databases only — export reminders, wages and periods before an owner-authorized rollback.

## 0019 — trusted devices for PIN sign-in

- `users.device_password_hash`: scrypt hash of the stronger password (≥ 8, letters and digits) that registers a new device for a PIN account. Null = no device can be registered yet.
- `trusted_devices`: one row per (device cookie, account); the cookie `manage_device` holds a random token, only its SHA-256 is stored. On a trusted device the PIN alone signs in; revoked rows (`revoked_at`) need the device password again.

Additive only. Rollback: the previous application ignores the table and column; `down/0019_staff_pin_devices.down.sql` is for disposable databases only.

## 0020 — six roles (spec section 3)

Five role codes plus the owner flag: `accident_expert`, `parts_clerk`, `technician`, `service_manager`, `system_admin`; the owner stays `users.is_owner`.

- `users.roles`: `accident_coordinator`, `accident_supervisor` and `qc_inspector` become `accident_expert` (duplicates removed); `cashier` is removed. An account left with no role and not the owner is kept but deactivated, and its open sessions are revoked. Credentials, PIN, Authenticator, personal allow/deny overrides, cases and audit are untouched.
- `tenants.permission_templates` is reset to `{}` (the code defaults of the specification) and `permission_version` is bumped, so open access forms reload.
- `reminders.target_role`: retired codes become `accident_expert` (`cashier` → null).
- New table `role_migration_log` keeps the previous and new value of every row the migration changed (`entity` = user | tenant | reminder). The application never writes it.

The application also maps any remaining legacy code when it reads roles (`normalizeRoles` in `packages/shared/src/enums.ts`), so a row written by an older image still resolves. Rollback: `down/0020_six_roles.down.sql` restores roles, active flags, templates and reminder roles exactly from the log, then drops it; revoked sessions stay revoked. Verified on PostgreSQL 16: 0000→0020 on an empty database, synthetic legacy rows mapped as described, down script restored every logged value.

## 0021 — price announcements (spec section 7)

New table `part_price_notices`: one row per «اعلام قیمت» of the parts clerk on one line (sale unit price, note, who and when) and the accident expert's answer (`approved` or `instruction` with text; `superseded` when a newer announcement, a cancellation or a return replaces it). Never blocks work; every write is audited. Lines (`part_requests.status`) and stock reservations (`stock_reservations.status`) may now also be `returned` (مرجوعی); both columns are text, so no constraint changes. The unified flow state of a line is derived, not stored: from status, source, `consumed_at` and the latest linked Emdad request (see `packages/shared/src/part-flow.ts`). `consumed_at` and `stock_reservations.reflected_at` are now set automatically when the case is finished (handover), which replaces the manual «reflect» step. Additive; the demo purge deletes the new rows. Verified on PostgreSQL 16 (0000→0021 and the down script). Rollback: `down/0021_part_price_notices.down.sql`, disposable databases only.
